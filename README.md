# მომხმარებელთა მიმართვების დამუშავება

## სტატუსი

- ნაწილი 1 — გასუფთავება და ანალიზი: შესრულებულია
- ნაწილი 2 — ვალუტის კონვერტაცია (NBG API): შესრულებულია
- ნაწილი 3 — LLM კლასიფიკაცია: შესრულებულია
- ნაწილი 4 — შედეგი და დოკუმენტაცია: მიმდინარე

## დაყენება და გაშვება

საჭიროა Python 3.10+, ინტერნეტთან კავშირი (NBG API) და Google Gemini-ის API key
(უფასოა: https://aistudio.google.com/apikey).

```bash
python -m venv venv
venv\Scripts\activate        # Linux/macOS: source venv/bin/activate
pip install -r requirements.txt
copy .env.example .env      # Linux/macOS: cp .env.example .env
                             # .env-ში ჩაწერეთ GEMINI_API_KEY=...
python main.py               # ან: python main.py path/to/requests.json
```

შედეგები იქმნება `output/` საქაღალდეში:

- `processed.json` — გასუფთავებული მიმართვები, დამატებითი ველებით `amount_gel`, `rate`, `rate_source`, `category` და `category_reason`;
- `rejected.json` — გამორიცხული ჩანაწერები (`record` — ორიგინალი, `reasons` — მიზეზები);
- `summary.json` — სტატისტიკა და გასწორებების ჟურნალი (`corrections`).

API key-ის გარეშეც პროგრამა ეშვება: კატეგორიები აიღება ქეშიდან
(`cache/classifications.json`), რომელიც რეპოზიტორიაშია ატვირთული.

შეიძლება რამდენიმე გამორიცხვის მიზეზი ჰქონდეს. ყველა გასწორება ფიქსირდება
`summary.json`-ის `corrections` ველში (`from` → `to`), რათა ცვლილება გამჭვირვალე იყოს.

  და დანარჩენი ჩანაწერების ფორმატს ეწინააღმდეგება.
- შეიძლება ბეჭდვის შეცდომაც იყოს (მაგ. `2026-03-05` ან `2026-12-05`).

  (`2026-05-12`) შორის მოხვდებოდა, ანუ ეს ვარაუდი რიგს ეწინააღმდეგება.
- არასწორი თარიღი თვეების სტატისტიკას დაამახინჯებდა, ამიტომ ჩანაწერი გამოირიცხა.

## ნაწილი 2: თანხების გადაყვანა ლარში

### გამოყენებული API

საქართველოს ეროვნული ბანკის (NBG) საჯარო API:

```
GET https://nbg.gov.ge/gw/api/ct/monetarypolicy/currencies/en/json/?date=2026-02-03
```

პასუხი (შემოკლებით):

```json
[{"date": "2026-02-03T00:00:00.000Z",
  "currencies": [{"code": "USD", "quantity": 1, "rate": 2.6902, ...}, ...]}]
```

### როგორ მუშაობს

- USD/EUR მიმართვისთვის გამოიყენება **მიმართვის თარიღით** დადგენილი კურსი.
- GEL-ის კურსია `1.0`, API არ გამოიძახება.
- ერთ თარიღზე API-ს ერთი მოთხოვნა იგზავნება, პასუხი ინახება ქეშში.
  ერთსა და იმავე თარიღზე API მეორედ არ გამოიძახება.
- კურსი ითვლება ერთ ერთეულზე: `rate / quantity`. USD/EUR-ს `quantity` = 1 აქვს,
  მაგრამ ზოგ ვალუტას (მაგ. AMD) 1000, ამიტომ ასე უფრო საიმედოა.
- `processed.json`-ში ემატება `rate_source`, რომ ჩანდეს, საიდან მოვიდა კურსი:
  - `gel` — თანხა უკვე ლარშია;
  - `nbg_request_date` — მიმართვის თარიღის კურსი;
  - `nbg_current` — მიმდინარე კურსი (სარეზერვო ვარიანტი);
  - `unavailable` — კურსი ვერ მოიძებნა.

### შეცდომების დამუშავება

1. ყოველ მოთხოვნას აქვს 10 წამიანი `timeout`.
2. Timeout, კავშირის შეცდომა, 5xx პასუხი ან არავალიდური JSON — მოთხოვნა მეორდება
   3-ჯერ, მზარდი პაუზით (1 წმ, 2 წმ).
3. 4xx პასუხზე მოთხოვნა არ მეორდება, რადგან განმეორება შედეგს არ შეცვლის.
4. თუ მიმართვის თარიღის კურსი ვერ მოიძებნა, გამოიყენება მიმდინარე კურსი
   (`rate_source: nbg_current`).
5. თუ API საერთოდ არ პასუხობს, `amount_gel` და `rate` არის `null`,
   `rate_source` — `unavailable`, პროგრამა კი მუშაობას აგრძელებს.
6. წარუმატებელი შედეგიც ინახება ქეშში, რომ ყოველ ჩანაწერზე 3 ცდა თავიდან არ დაიწყოს.

შემოწმებული სცენარები:

- არარსებული მისამართი (`NBG_API_URL=https://nbg.invalid/api/`): პროგრამა
  არ ჩერდება, USD/EUR ჩანაწერებს ენიჭება `unavailable`, GEL ჩანაწერები კი გადაიყვანება.
- თარიღიანი მოთხოვნის ხელოვნური შეცდომა: გამოიყენება მიმდინარე კურსი (`nbg_current`).

## ნაწილი 3: მიმართვების კლასიფიკაცია LLM-ით

### მოდელის არჩევა

- **Google Gemini** — უფასო ტარიფი, საკრედიტო ბარათი არ სჭირდება, ქართულს კარგად იგებს.
- მოდელი: `gemini-3.1-flash-lite` (შეცვლა შეიძლება `.env`-ში `GEMINI_MODEL`-ით).
- SDK: ოფიციალური `google-genai` ბიბლიოთეკა.

### როგორ მუშაობს

- თითოეული მიმართვის ტექსტი ცალკე მოთხოვნით იგზავნება.
- სისტემურ ინსტრუქციაში (`SYSTEM_PROMPT`, `src/classifier.py`) აღწერილია
  ოთხივე კატეგორია და წესი: თუ მიმართვა რამდენიმეს შეესაბამება, აირჩიოს მთავარი მიზანი.
- **Structured output:** პასუხი JSON სქემით არის შეზღუდული
  (`response_mime_type="application/json"` + `response_json_schema`).
  `category` შეიძლება იყოს მხოლოდ ოთხიდან ერთ-ერთი (`enum`), ამიტომ მოდელი
  ახალ კატეგორიას ვერ მოიგონებს და თავისუფალ ტექსტს ვერ დააბრუნებს.
- `reason` ველში მოდელი ერთი წინადადებით ხსნის არჩევანს. ეს ხელით შემოწმებას ამარტივებს
  და `processed.json`-ში `category_reason`-ად ინახება.
- `temperature=0`, რომ ერთსა და იმავე ტექსტზე პასუხი მაქსიმალურად სტაბილური იყოს.
- პასუხი მაინც მოწმდება კოდში: არავალიდური JSON ან უცნობი კატეგორია ხელახლა ითხოვება.

### შეცდომები და ქეში

- 429 (უფასო ტარიფის ლიმიტი) და 5xx — მოთხოვნა მეორდება 5-ჯერ, მზარდი პაუზით (5, 10, 20, 40 წმ).
- მოთხოვნის ლიმიტი 60 წამია.
- თუ ჩანაწერი მაინც ვერ დაკლასიფიცირდა, `category` = `null`, პროგრამა აგრძელებს მუშაობას,
  `summary.json`-ში კი ჩანს როგორც `unclassified`.
- ყოველი პასუხი ინახება `cache/classifications.json`-ში (გასაღები: id + ტექსტის hash).
  ხელახლა გაშვებისას API არ გამოიძახება. ტექსტი თუ შეიცვლება, hash შეიცვლება
  და ჩანაწერი თავიდან დაკლასიფიცირდება.

## სირთულეები და მათი გადაჭრა

- **API-ის დოკუმენტაცია.** NBG-ის საიტზე API-ს ცალკე დოკუმენტაცია არ არის.
  endpoint-ს იყენებს კურსების გვერდი (nbg.gov.ge/monetary-policy/currency).
  პარამეტრები და პასუხის სტრუქტურა `curl`-ით შემოწმდა.
- **`currencies` პარამეტრი არასაიმედოა.** API შეცდომის ნაცვლად ცარიელ სიას `[]` აბრუნებს:
  - `currencies=USD,EUR` — ყოველთვის `[]`;
  - `currencies=USD&currencies=EUR` — `date`-ით მუშაობს, `date`-ის გარეშე კი `[]`.

  ეს მეორე შემთხვევა სარეზერვო (მიმდინარე) კურსის ტესტირებისას გამოჩნდა.
  გადაწყვეტა: ფილტრი საერთოდ არ გამოიყენება. ერთი მოთხოვნა ყველა ვალუტას
  აბრუნებს (~40), USD და EUR კი კოდში ამოირჩევა. ცარიელი პასუხი შეცდომად ითვლება.
- **შაბათ-კვირა.** REQ-005-ის თარიღი (2026-02-14) შაბათია. API ამ დღისთვისაც აბრუნებს
  კურსს, ამიტომ ცალკე დამუშავება არ დასჭირდა.
- **Gemini-ის მოდელის ხელმისაწვდომობა.** ხელმისაწვდომი მოდელების სია `client.models.list()`-ით
  მივიღე და რამდენიმე ერთი ტესტური მოთხოვნით შევამოწმე:
  - `gemini-2.5-flash` — `404 NOT_FOUND`: „no longer available to new users“;
  - `gemini-3.8-flash`, `gemini-3.5-flash`, `gemini-flash-latest` — `503 UNAVAILABLE` (high demand);
    `gemini-3.8-flash`-მა შეცდომის დაბრუნებამდე 138 წამი იცადა;
  - `gemini-3.1-flash-lite` — უპასუხა 1.4 წამში.

  გადაწყვეტა: ნაგულისხმევი მოდელი `gemini-3.1-flash-lite` (4 კატეგორიისთვის საკმარისია),
  მოთხოვნის ლიმიტი 60 წამი, მოდელის შეცვლა კი შეიძლება `.env`-ით.
- **ქართული ტექსტი Windows-ის კონსოლში.** კატეგორიების დაბეჭდვისას `UnicodeEncodeError`
  (კონსოლი cp1252-ს იყენებს). გადაწყვეტა: `sys.stdout.reconfigure(encoding="utf-8")`.
- **API key-ის უსაფრთხოება.** გასაღები ინახება `.env`-ში, რომელიც `.gitignore`-შია.
  რეპოზიტორიაში მხოლოდ ცარიელი შაბლონია (`.env.example`).

## ახალი შესწავლილი საკითხები

**Python და მონაცემების დამუშავება**

- **HTTP მოთხოვნები Python-ში `requests`-ით:** `fetch`/`axios`-ის ნაცვლად. სხვაობა:
  `requests`-ს ნაგულისხმევად timeout არ აქვს და მოთხოვნა შეიძლება უსასრულოდ დაელოდოს,
  ამიტომ `timeout` ყველგან ხელით უნდა მიეთითოს.

- **ფაილების კოდირება:** `encoding="utf-8"` და `ensure_ascii=False` ქართული ტექსტის
  JSON-ში შესანახად; Windows-ის კონსოლის cp1252 კოდირების პრობლემა, რომელიც ბრაუზერში
  არ არსებობს.

- **Structured output:** LLM-ის პასუხის შეზღუდვა JSON სქემით
  (`response_json_schema`, `enum`), რომ მოდელმა მხოლოდ დაშვებული კატეგორია დააბრუნოს.

- **Prompt-ის შედგენა:** სისტემური ინსტრუქცია (`system_instruction`), კატეგორიების
  მკაფიო განსაზღვრება, `temperature=0` სტაბილური პასუხისთვის, `reason` ველი
  მოდელის არჩევანის შესამოწმებლად.
- **LLM-ის შედეგის შეფასება:** მოდელის პასუხი საბოლოო ჭეშმარიტება არ არის. ხელით
  შემოწმებისას გამოჩნდა არათანმიმდევრულობა მსგავს მიმართვებზე (REQ-001 vs REQ-004).
- **LLM-ის პასუხების ქეშირება:** ფაილში შენახვა (id + ტექსტის hash), რომ ხელახალი
  გაშვებისას API არ გამოიძახოს და უფასო ლიმიტი არ დაიხარჯოს.
